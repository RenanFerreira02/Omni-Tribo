## 1. Índice GiST — CONFORME, com nuance que merece leitura atenta

A especificação alerta: *"Se aparecer Seq Scan, procure por `ST_Distance(...) < X` sem `ST_DWithin`"*.

**Não há Seq Scan em nenhum plano, e não existe `ST_Distance(...) < X` no código.** Todas as
ocorrências de `ST_Distance` estão em `SELECT` (projeção do valor) ou em javadoc; o predicado é
sempre `ST_DWithin`, que é o que usa índice.

Mas o plano da query real, na base de seed, é este:

```
EXPLAIN (ANALYZE) — query da aplicação, com filtro de status, enable_seqscan = on

 Limit
   ->  Sort  (Sort Key: st_distance(origem, ...))
         ->  Index Scan using idx_missao_expiravel on missao m
               Filter: st_dwithin(origem, ..., '2000', true)
               Rows Removed by Filter: 1
 Execution Time: 4.761 ms
```

O planner escolheu **`idx_missao_expiravel`** (B-tree parcial sobre `janela_fim WHERE status =
'ABERTA'`), e o `ST_DWithin` virou `Filter` em vez de `Index Cond`. Isolei a causa com duas
variantes:

```
(a) MESMA query, SEM o filtro de status:
      Index Scan using idx_missao_origem            ← GiST
        Index Cond: (origem && _st_expand(..., '2000'))
        Filter: st_dwithin(...)

(b) COM status, derrubando o índice parcial concorrente (em transação revertida):
      Index Scan using idx_missao_status_criada     ← outro B-tree de status
        Index Cond: ((status)::text = 'ABERTA')
        Filter: st_dwithin(...)
      Execution Time: 0.022 ms
```

**Diagnóstico:** com 12 missões no seed, das quais 5 estão ABERTA, o filtro de status é mais seletivo
que o de proximidade. O planner está **certo** em preferir o B-tree — e a prova disso é a variante
(b), que roda em 0,022 ms contra 4,7 ms. Trocar o índice degradaria a consulta.

**A evidência de que o GiST é usado quando é o caminho seletivo já existe no repositório**, e o
projeto antecipou este exato fenômeno. `docs/evidencias/f6-explain-analyze.md` traz o plano sobre
**200 mil linhas**, com `"Node Type": "Index Scan"` e `"Index Name": "idx_missao_origem"`. O javadoc
de `IndiceGeoespacialTest` explica a metodologia:

> *"Todas as 200 mil linhas sintéticas nascem ABERTA de propósito: isso torna `idx_missao_status`
> [inútil] … com status misturado, o planner poderia legitimamente preferir o B-tree e a prova seria
> sobre o [índice errado]."*

E o teste chama `ANALYZE missao` antes do `EXPLAIN`, com o motivo comentado: sem estatísticas
coletadas, o PostGIS cai num palpite fixo de seletividade e o plano deixa de ser evidência.

**Classifico como CONFORME.** O índice existe (`idx_missao_origem`, GiST, criado na V8), a query usa
`ST_DWithin` corretamente, e o índice é escolhido quando é o caminho seletivo. Registro a nuance
porque um `EXPLAIN` rodado numa base de dev mostra o GiST *não* sendo usado, o que se lê facilmente
como defeito — e não é.

## 2. PostGIS confinado a uma classe — CONFORME (excedente)

```
arquivos com padrão "ST_":
  ConsultasGeoespaciais.java  → 11   ← única com chamadas reais
  AuditoriaAspecto.java       →  3   ← falso positivo: "LOWEST_PRECEDENCE"
  Geohash.java                →  1   ← javadoc
  MissaoProximaResponse.java  →  1   ← javadoc
  MissaoController.java       →  1   ← texto de @Operation do OpenAPI
```

**`compartilhado/infra/ConsultasGeoespaciais` é o único arquivo com chamada PostGIS de verdade.** Os
três "restantes" são documentação, e os de `AuditoriaAspecto` nem são PostGIS — o grep casou com
`LOWEST_PRECEDENCE`.

O objetivo declarado na especificação — *"permite trocar por Oracle Spatial em um arquivo"* — está
explícito no javadoc da classe, com o mapeamento pronto:

> *"Trocar PostGIS por Oracle Spatial é reescrever este arquivo e mais nada: `ST_DWithin` →
> `SDO_WITHIN_DISTANCE`, `ST_Distance` → `SDO_GEOM.SDO_DISTANCE`."*

**Excedente, e é a parte interessante:** a classe não é um repositório Spring Data, e a razão está
comentada — `@Query(nativeQuery=true)` exigiria interface ligada a uma `@Entity`, e a única entidade
visível de `compartilhado` seria `Outbox`. Usa `JdbcClient`, que participa da transação corrente. E
há uma restrição de desenho que decorre da regra do ArchUnit ser **direcional**: `compartilhado` é
isento como alvo, mas continua sendo *origem*, então `ConsultasGeoespaciais` **não pode importar**
`Missao`, `StatusMissao` nem `CategoriaMissao`. Por isso status e categoria entram como `String`
(sempre `.name()` de enum já validado pelo binder, nunca texto livre do cliente) e o retorno é
`AlvoProximo`, um par neutro id+distância que o chamador reidrata.

Parâmetros são todos bindados, com `CAST(:param AS ...)` explícito — o comentário registra que um
parâmetro nulo sem tipo chega ao PostgreSQL como `bytea` e a consulta estoura com *"function … does
not exist"*. Zero concatenação.

## 3. Limites de raio, 49 m × 51 m — CONFORME

Missão criada com `raio_checkin_m = 50`, levada a EM_ANDAMENTO com bob como executor. As coordenadas
foram geradas pelo próprio PostGIS, para que a distância seja exata e não aproximada:

```sql
ST_Project(ST_SetSRID(ST_MakePoint(-46.6934, -23.5640), 4326)::geography, 49, radians(0))
  → -23.563557569919304, -46.6934
ST_Project(..., 51, radians(0))
  → -23.563539511548120, -46.6934
```

**Resultado:**

```
a 51 m  →  422   (rejeitado)
a 49 m  →  200   status da missão passou a AGUARDANDO_CONFIRMACAO
```

E a distância que o servidor **calculou e gravou**, confirmando que a medição é dele:

```
 dist_m | valido
--------+--------
   51.0 |   f
   49.0 |   t
```

## 4. Acurácia e localização simulada — CONFORME

```
acuraciaM = 200   →  422
mocked = true     →  422
```

Constantes em `AvaliacaoAntifraude.java:25,28` — `ACURACIA_MAXIMA_M = 50`,
`VELOCIDADE_SUSPEITA_KMH = 120`.

**Nuance de desenho que vale registrar:** `mocked` é `Boolean` e não `boolean`, e o javadoc do DTO
explica que campo JSON ausente não binda em primitivo — ausente equivale a `false`. O comentário
segue: *"quem não reporta mock é indistinguível de quem reporta false, e é justamente por isso que
esta flag sozinha não é uma defesa."* A honestidade está no lugar certo: no código, não só na
documentação.

## 5. Rejeições persistidas com motivo — CONFORME (excedente)

Consulta à tabela após as quatro tentativas:

```
 dist_m | acuracia_m | mock_detectado | valido |                     motivo
--------+------------+----------------+--------+------------------------------------------------
   51.0 |      10.00 | f              | f      | Você está a 51 m da origem da missão; o raio p…
    0.0 |     200.00 | f              | f      | Precisão do GPS insuficiente (200 m). O máximo…
    0.0 |      10.00 | t              | f      | Localização simulada detectada pelo dispositiv…
   49.0 |      10.00 | f              | t      | —
```

As três rejeições estão gravadas, com `motivo_rejeicao` preenchido, `mock_detectado` marcado no caso
certo, e a distância medida pelo servidor em cada uma. A trilha é append-only.

**Excedente, e é o detalhe mais difícil desta fase:** persistir a rejeição *e* devolver 422 é
contraditório numa transação — lançar a exceção apagaria a linha no rollback. A primeira
implementação resolveu com `REQUIRES_NEW` e **estava errada**: a transação externa segura
`FOR UPDATE` sobre a missão enquanto a interna pede uma segunda conexão, então bastava concorrência ≥
tamanho do pool para travar a aplicação inteira, inclusive o login. Só apareceu quando
`CheckinConcorrenteTest` foi escrito com 50 threads.

A correção não foi aumentar o pool: o serviço passou a devolver a recusa como **valor**
(`ResultadoRegistroCheckin`), a transação commita nos dois casos, e o **controller** lança o 422
depois do commit. Uma transação, uma conexão — e de quebra o caminho aceito ficou atômico, o que
antes não era: havia uma janela em que a linha de check-in existia sem a transição correspondente.

## 6. O cliente pode enviar a distância? — CONFORME

**Não. O campo não existe.** `RegistrarCheckinRequest` tem exatamente quatro componentes:

| Campo | Validação |
|---|---|
| `lat` | `@NotNull`, faixa −90..90 |
| `lon` | `@NotNull`, faixa −180..180 |
| `acuraciaM` | `@NotNull`, 0..10000 |
| `mocked` | `Boolean`, ausente = false |

Não há `distancia`, `distanciaM` nem equivalente. O javadoc do record declara:

> *"A distância até a origem é calculada no SERVIDOR por PostGIS e comparada com raio_checkin_m —
> nenhum valor de distância informado pelo cliente é aceito."*

E a prova empírica está no item 3: enviei apenas lat/lon, e a coluna `distancia_alvo_m` foi
preenchida com 51,0 e 49,0 — valores que o servidor derivou. Mesmo que o cliente tentasse enviar um
campo `distancia`, ele seria descartado silenciosamente por `fail-on-unknown-properties: false`, que
é decisão explícita de proteção contra mass assignment.

## 7. `Idempotency-Key` — CONFORME

```
sem o header                      →  400
com chave nova (49 m)             →  200   → 1 linha em checkin
replay da MESMA chave             →  200   → nenhuma linha nova

total de linhas na missão: 4   (3 rejeições + 1 sucesso; o replay não gerou a 5ª)
linhas com valido = true:  1
```

Header obrigatório com `@NotBlank @Size(min = 8, max = 200)`.

**Detalhe de segurança que vale citar:** a chave do cliente **não é armazenada crua**. O check-in
guarda `sha256(usuario | missao | chave_do_cliente)` — porque a UNIQUE é global, e com a chave crua o
cliente que mandasse `"1"` receberia o replay do check-in alheio. Coberto por
`chave_de_cliente_igual_vinda_de_outro_usuario_nao_colide`.

## Itens adicionais da especificação — CONFORME

### Só em EM_ANDAMENTO, com executor == usuário do token

```
diana (não é executora)                        →  403
bob, com a missão já em AGUARDANDO_CONFIRMACAO →  409
```

A ordem de checagem é **403 → sondagem de idempotência → 409 → gravação**, e a posição da sondagem no
meio é deliberada: um replay legítimo chega com a missão já em `AGUARDANDO_CONFIRMACAO` e levaria
409; e ela fica depois do 403 porque antes dele um não-executor receberia dados da missão. É por isso
que `MissaoStateMachine.validarAutorizacao` é pública.

### Cinemática acima de 120 km/h

`AvaliacaoAntifraude.java:113` compara com `VELOCIDADE_SUSPEITA_KMH = 120`. A coluna
`velocidade_implicita_kmh` foi preenchida em **3 das 4** linhas — nula apenas na primeira, porque não
há check-in anterior desse usuário com que comparar.

**Comportamento correto e não óbvio:** velocidade implausível **não rejeita**, marca `suspeito`.
Coberto por `CheckinControllerTest.velocidade_implausivel_aceita_mas_marca_suspeito:418`. Presença
comprovada não é execução comprovada, e transformar um sinal fraco em bloqueio produziria falso
positivo em quem legitimamente viajou de carro entre duas missões.

Dois bugs desta lógica foram achados pelos próprios testes de integração e corrigidos **no cálculo,
não na assertion**: `Duration.toSeconds()` truncava, e dois check-ins a menos de 1 s davam velocidade
nula — o teleporte *mais* implausível era o único não sinalizado; e o cálculo em milissegundos expôs
estouro de `NUMERIC(10,2)` num deslocamento intercontinental, que derrubava o check-in com 500 em vez
de marcá-lo. Hoje satura no máximo da coluna, porque o número é sinal, não medida.

### Transição pela máquina de estados

Verificado em runtime: o check-in aceito levou a missão a `AGUARDANDO_CONFIRMACAO`. E na auditoria F5
foi confirmado que `missao.setStatus()` tem um único chamador em todo o código —
`MissaoStateMachine.java:39`.

### Honestidade documentada

`docs/seguranca/antifraude-geolocalizacao.md` registra o que os controles **não** pegam: spoofing com
root ou emulador é mitigável e não eliminável, `mocked` é reportado pelo cliente, presença não é
execução, conluio não é detectado, e a cinemática é cega no primeiro check-in de cada conta.

## Ordem por impacto

**Nenhuma correção necessária.** Duas observações, ambas de documentação:

1. **Registrar a nuance do planner** — `docs/evidencias/f6-explain-analyze.md` prova o GiST sobre 200
   mil linhas, mas não menciona que na base de seed o planner escolhe o B-tree de status, e que isso
   é correto. Quem rodar `EXPLAIN` em dev vai ver o GiST ausente e concluir que há defeito. Uma
   seção curta com as três variantes deste relatório evitaria o falso alarme.
2. **`idx_missao_expiravel` e `idx_missao_status_criada` competem pela mesma consulta** — os dois
   servem ao filtro de status, e na base de seed o planner alternou entre eles conforme a
   disponibilidade. Não é problema hoje; vale reavaliar na F12, quando houver dado de volume real,
   se ambos se justificam.

Nota de encerramento: esta é a segunda fase auditada sem nenhum achado corretivo — e a única em que
todos os sete itens de verificação da especificação foram confirmados por execução, e não por leitura
de código.
