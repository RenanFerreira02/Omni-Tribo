## 3. CLAUDE.md — DEFEITO + LACUNA

### 3a. Regra de cálculo de recompensa no servidor — **DEFEITO (grave)**

A especificação exige que o CLAUDE.md contenha "regras de cálculo de recompensa no servidor". Ele
não contém — e a razão é mais séria que uma omissão de documentação: **a regra não existe no
código.** O cliente escolhe a própria recompensa.

`services/api/src/main/java/com/omnitribo/missoes/api/CriarMissaoRequest.java:42,45`

```java
        long tokensRecompensa,          // ← enviado pelo cliente, @Max(1000)
        int  xpRecompensa,              // ← enviado pelo cliente, @Max(5000)
```

`services/api/src/main/java/com/omnitribo/missoes/dominio/MissaoService.java:128,130` grava os dois
valores direto na entidade. Uma varredura por `calcularRecompensa|RegraRecompensa|complexidade` em
todo `src/main/java` **não retorna nada**: não há cálculo no servidor em lugar nenhum.

**Isso é a impressora de dinheiro do ADR 0009, reencarnada no TOKEN.** As categorias ENTREGA e AJUDA
não pagam do pote (pendência #3 do CLAUDE.md), então a recompensa delas é *cunhada*. Somando as duas
coisas — cliente escolhe o valor, e o valor é cunhado — dois usuários combinados emitem moeda à
vontade. Medido contra a API em execução:

```
TOKEN no sistema (carteiras + potes) ANTES:  656
  ciclo 1, tokensRecompensa=1000 escolhido pelo cliente → 1656
  ciclo 2, tokensRecompensa=1000 escolhido pelo cliente → 2656
TOKEN no sistema DEPOIS: 2656          (+2000 do nada, teto de 1000/missão)

Reconciliação: {"carteirasVerificadas":6,"integro":true,"divergencias":[]}
```

A reconciliação responde `integro=true` pela mesma razão de antes, e continua correta: ela compara
ledger com projeção, não verifica conservação. **É mais grave que o caso do BRL**, porque o BRL era
escritural e sem saque, enquanto o TOKEN é a moeda que o ADR 0009 tornou central e que resgata
benefício real de parceiro.

Correção tem duas metades, e uma só não basta:
1. `xpRecompensa` e `tokensRecompensa` saem de `CriarMissaoRequest` (mesma disciplina que já removeu
   `status`, `executorId` e `criadorId` — ver o javadoc do próprio DTO, linhas 20-23);
2. servidor deriva a recompensa de categoria + complexidade (peso, volume, distância origem→destino,
   janela), numa classe de regra testável.

Sem a segunda metade, a primeira só congela o valor em zero. Enquanto ENTREGA/AJUDA cunharem, o teto
da emissão passa a ser a tabela de recompensa em vez do arbítrio do cliente — o que reduz o dano mas
não fecha; o fechamento é a carteira de patrocinador da F8.

## 4. `.claude/` — DEFEITO + LACUNA

### 4a. Permissões — CONFORME (excedente)

`.claude/settings.json:18-30` nega tudo o que a especificação pede, e mais:

```json
"deny": [ "Bash(git push --force*)", "Bash(git push -f*)", "Bash(git reset --hard*)",
          "Bash(rm -rf *)", "Bash(docker compose down -v*)",
          "Read(./.env)", "Read(./**/.env)", "Read(./**/google-services.json)",
          "Read(./**/*.jks)", "Read(./**/*.p8)", "Read(./**/*.keystore)" ]
```

**Observação sobre alcance, não defeito:** `deny` casa a linha de comando do `Bash`, não os
subprocessos. `make reset` executa `docker compose down -v` internamente e **não** é barrado pela
regra `Bash(docker compose down -v*)`. Isso é comportamento esperado da ferramenta, mas vale saber:
o alvo `reset` do Makefile é destrutivo e passa pela malha.

### 4b. Hook de checagem de segredo — **DEFEITO**

```
-rw-r--r--. 1 renan renan 379 .claude/hooks/checar-segredo.sh
```

**O arquivo não tem bit de execução.** `.claude/settings.json:33-35` o registra como
`"type": "command"` em `PreToolUse`. Sem `+x`, a invocação falha, e a falha de um hook não interrompe
o commit — ou seja, **a segunda barreira contra segredo no diff não está ativa**, e o modo como ela
falha é silencioso. Correção: `chmod +x .claude/hooks/checar-segredo.sh` e commit do bit.

Atenuante: o Gitleaks do `security.yml` cobre o mesmo risco no CI, então não há exposição real hoje —
mas ele roda *depois* do push, e o hook existe justamente para agir antes.
