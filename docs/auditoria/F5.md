# Auditoria F5 — Módulo de missões

**Data:** 2026-08-08 · **Branch:** `develop` · **HEAD:** `a3edef7`
**Método:** inventário completo do DTO de criação; varredura do código por lógica de cálculo; leitura
do serviço de conclusão e da máquina de estados; e **exercício em runtime** — criação de missão com
recompensa arbitrária seguida de consulta ao banco, e ciclo completo de pote TRIBO com verificação de
saldo e ledger. **Nenhum arquivo alterado.**

## Veredito

O **ciclo de vida** desta fase é exemplar: máquina de estados centralizada com chamador único de
`setStatus`, matriz de 99 combinações testada contra tabela escrita à mão, aceite concorrente com um
vencedor, pote TRIBO reservando e devolvendo corretamente.

A **economia** — que a especificação chama de núcleo da fase — **não está implementada**. Não é uma
lacuna parcial: a `CalculadoraDeRecompensa` não existe, `versao_formula` não existe, o endpoint de
prévia não existe, e o DTO de criação aceita a recompensa do cliente. Os quatro são o mesmo buraco
visto de ângulos diferentes.

| Verificação | Classificação |
|---|---|
| **A** · DTO aceita recompensa do cliente | **DEFEITO CRÍTICO** |
| **B** · `CalculadoraDeRecompensa` | **LACUNA** (alta) — não existe |
| **C** · `versao_formula` congelada | **LACUNA** (alta) — não existe |

## A) O DTO de criação aceita recompensa do cliente — **DEFEITO CRÍTICO**

`CriarMissaoRequest.java` tem **21 componentes**. Dois não deveriam estar lá:

```
 1. CategoriaMissao categoria          12. String logradouro
 2. String titulo                      13. String bairro
 3. String descricao                   14. String cidade
 4. BigDecimal valorBrl                15. String uf
 5. long tokensRecompensa   ← linha 42 16. int raioCheckinM
 6. int xpRecompensa        ← linha 45 17. BigDecimal pesoKg
 7. BigDecimal origemLat               18. BigDecimal volumeL
 8. BigDecimal origemLon               19. Instant janelaInicio
 9. BigDecimal destinoLat              20. Instant janelaFim
10. BigDecimal destinoLon              21. UUID pontoCustodiaId
11. String cep
```

`MissaoService.java:128,130` grava `req.xpRecompensa()` e `req.tokensRecompensa()` direto na
entidade, sem passar por nada.

**Prova executada, via HTTP contra a API em execução:**

```
POST /api/v1/missoes
{
  "categoria": "AJUDA",
  "titulo": "Missao trivial: apertar um parafuso",
  "descricao": "Trabalho de 30 segundos. A recompensa quem define sou eu, o criador.",
  "tokensRecompensa": 1000,
  "xpRecompensa": 5000,
  ...
}
→ 201 Created
```

E o que ficou **no banco**:

```
               titulo                | categoria | xp_recompensa | tokens_recompensa | peso_kg | volume_l | sem_destino
-------------------------------------+-----------+---------------+-------------------+---------+----------+-------------
 Missao trivial: apertar um parafuso | AJUDA     |          5000 |              1000 |         |          | t
```

**Máximo de XP e máximo de tokens que o sistema permite, numa missão sem peso, sem volume e sem
destino** — ou seja, com *nenhum* dos insumos que a especificação lista para o cálculo. O único
controle é `@Max`, que é teto, não cálculo:

```
tokensRecompensa: 5000 → 400  "Máximo de 1000 tokens por missão"
xpRecompensa: 99999   → 400  "Máximo de 5000 XP por missão"
```

Um teto sem fórmula significa que **toda missão pode valer o teto**, e a única variável é a vontade
de quem cria.

**O vetor de abuso é o mesmo do `valorBrl` que o ADR 0009 fechou, agora em token** — e é pior, por
três razões concretas:

1. **O TOKEN é a moeda que resgata benefício real de parceiro.** O BRL era escritural e com saque
   desligado; o token, não.
2. **ENTREGA e AJUDA cunham** (pendência #3 do CLAUDE.md): `pagaTokensDoPote` cobre só TRIBO e
   COLETA, então a recompensa dessas categorias sai do nada. A categoria escolhida na prova acima —
   AJUDA — é exatamente uma delas.
3. **A reconciliação não pega.** Medido na auditoria F0: o total do sistema foi de 656 para 2656
   tokens em dois ciclos, e `GET /admin/carteiras/reconciliacao` respondeu
   `{"integro":true,"divergencias":[]}` o tempo todo. Ela compara ledger com projeção; conservação
   não é objeto dela.

Este é o achado de maior impacto de toda a auditoria, F0 a F5.

## B) `CalculadoraDeRecompensa` — **LACUNA (alta)**

```
grep -rniE "calculadora|calcularRecompensa|RegraRecompensa|complexidade|multiplicador|formula"
     src/main/java  →  NENHUMA ocorrência
```

Não há classe, método, nem menção. Conteúdo real de `missoes/dominio/`:

```
AtorEsperado · AtorMissao · CategoriaMissao · EstornoFinanciamentoService · EventoMissao
ExpiracaoMissoesService · FinanciamentoService · Missao · MissaoEvento · MissaoService
MissaoStateMachine · StatusMissao · TipoMissaoEvento
```

A especificação pergunta *"se estiver dentro de um service com dependência de repositório, aponte"*.
Não é o caso — **não existe em lugar nenhum**, nem em forma degradada. Não há o que refatorar; há o
que criar.

Os insumos exigidos pela spec existem parcialmente no modelo:

| Insumo | Situação |
|---|---|
| categoria | ✅ `missao.categoria` |
| peso, volume | ✅ `peso_kg numeric(6,2)`, `volume_l numeric(8,2)` |
| distância origem→destino | ✅ derivável por PostGIS a partir de `origem`/`destino` |
| janela | ✅ `janela_inicio`, `janela_fim` |
| **complexidade** | ❌ **coluna não existe** (ver `docs/auditoria/F3.md`, item 4) |

Ou seja: a calculadora depende de uma coluna que a F3 também apontou como ausente. **As duas entram
juntas ou nenhuma funciona.**

## C) `versao_formula` congelada — **LACUNA (alta)**

```
grep -rn "versao_formula\|versaoFormula" src/main/  →  NENHUMA ocorrência
```

Nem coluna, nem campo, nem código que preencha. Confirmado também no `\d+ missao` da F3.

**Por que isso importa mais do que parece**, e a especificação está certa ao destacar: sem registrar
qual fórmula produziu cada valor, mudar os parâmetros amanhã **reinterpreta retroativamente** toda
missão já criada. Duas consequências distintas:

- **Quebra o acordo com quem aceitou.** Alguém aceitou uma missão por 30 tokens; se a tabela mudar,
  não há registro de que 30 era o valor correto no momento do aceite.
- **Quebra a auditabilidade que o ledger constrói.** O ledger guarda `saldo_apos_*` justamente para
  que cada linha seja verificável no contexto em que foi escrita. A recompensa não tem o equivalente:
  é impossível responder "este crédito de 30 tokens estava certo?" sem saber qual fórmula valia.

É o mesmo princípio de `saldo_apos_*`, aplicado à origem do valor em vez de ao efeito dele.

## D) A recompensa é recalculada na conclusão? — **CONFORME**

**Não é.** O serviço lê o valor congelado na entidade:

| Linha | Código |
|---|---|
| `MissaoService.java:579` | `long tokens = missao.getTokensRecompensa();` |
| `MissaoService.java:602` | `progressaoUsuario.concederXp(executorId, missao.getXpRecompensa());` |
| `MissaoService.java:312` | `long recompensa = missao.getTokensRecompensa();` (guarda de publicação) |

Nenhuma chamada a calculadora — o que é trivialmente verdade, já que ela não existe, mas o padrão de
leitura está correto e **continuará correto quando a calculadora entrar**: o ponto de conclusão já lê
da entidade, não de uma fonte derivada.

**Ressalva importante:** hoje "congelado" significa apenas "gravado na criação". Sem `versao_formula`
(item C), o valor é congelado mas **não é auditável** — sabe-se *quanto*, não *por quê*.

## E) A máquina de estados é uma classe? — **CONFORME (excedente)**

Centralizada, e com uma propriedade forte: **`missao.setStatus()` tem exatamente um chamador em todo
o código de produção.**

```
grep -rn "\.setStatus(" src/main/java  (excluindo response.setStatus e Usuario)
  → src/main/java/com/omnitribo/missoes/dominio/MissaoStateMachine.java:39
```

Não existe atalho possível: qualquer mudança de status passa por `MissaoStateMachine`. Os dez pontos
de chamada em `MissaoService` e `ExpiracaoMissoesService` usam `transicionar`, `validar`,
`validarAutorizacao` ou `validarEdicao`.

A tabela de transições vive em `StatusMissao` (bloco `static`, 13 transições), e o ator autorizado
vive em `EventoMissao` — `CRIADOR`, `EXECUTOR`, `CANDIDATO`, `ADMIN`, `SISTEMA`. A separação é
deliberada e está comentada: `EventoMissao` nunca referencia `StatusMissao`, para evitar ciclo de
inicialização estática entre enums.

**Os dois `if` que sobrevivem em `MissaoService` NÃO são atalhos de transição:**

```java
// MissaoService.java:382 e 702
if (missao.getStatus() == StatusMissao.RASCUNHO && !ator.ehMesmo(missao.getCriadorId())) {
    throw new RecursoNaoEncontradoException(NAO_ENCONTRADA);
}
```

É regra de **visibilidade** — rascunho alheio responde 404 e não 403, para não confirmar existência
(ver `docs/auditoria/F4.md`, item 5). Não decide transição.

## Demais itens da especificação

### Economia

| Item | Situação |
|---|---|
| `valor_brl = 0` obrigatório em todas as categorias | **CONFORME** — `ck_missao_economia` (V15) verificado com INSERT nas 4 categorias na F3; validação devolve 400 apontando `valorBrl`, testado por `nenhumaCategoriaAceitaValorEmBrl` (parametrizado nas 4) |
| DTO sem `xpRecompensa`/`tokensRecompensa` | **DEFEITO** — item A |
| `CalculadoraDeRecompensa` | **LACUNA** — item B |
| Congelamento com `versao_formula` | **LACUNA** — item C |
| `POST /missoes/previa-recompensa` | **LACUNA** — `grep "previa\|preview"` nos controllers: nenhuma ocorrência. Depende inteiramente de B |
| Publicação TRIBO reserva o pote; cancelar/expirar devolve | **CONFORME** — exercitado abaixo |

**Ciclo do pote, executado em runtime:**

```
TRIBO criada (30 tk de recompensa) · carol: 200 tk · pote: 0
1) publicar SEM pote  → 422        (guarda de publicação)
2) financiar 30 tk    → 201        carol: 170 tk · pote: 30
3) publicar COM pote  → 200        pote: 30
4) cancelar           → 200        carol: 200 tk · pote: 0

lançamentos gerados:
  sinal  |       motivo        | valor_tokens
---------+---------------------+--------------
 DEBITO  | FINANCIAMENTO_TRIBO |           30
 CREDITO | ESTORNO             |           30
```

Saldo volta ao original, pote zera, e ambos os movimentos ficam no ledger append-only.

**Nuance de vocabulário, não defeito:** a especificação diz *"publicação reserva o pote"*. Na
implementação, a **reserva acontece no financiamento** (`POST /tribos/{id}/financiamentos`), e a
publicação apenas **valida** que o pote cobre a recompensa. O efeito econômico é o mesmo — token não
circula sem lastro —, mas os dois passos são distintos e o financiamento pode ser coletivo, com
vários financiadores antes da publicação. A F3 aponta que o desenho-alvo separa isso em tabela `pote`
com `status RESERVADO/PAGO/DEVOLVIDO`, o que tornaria a reserva explícita em vez de implícita no
saldo.

**Estorno tem dois pontos de chamada, e isso é deliberado:** `MissaoService.aplicar` e
`ExpiracaoMissoesService.expirarLote`. O job de expiração é o único caminho para EXPIRADA e não passa
por `aplicar()`; sem a chamada lá, os tokens ficariam presos numa missão morta **e a reconciliação
continuaria respondendo `integro=true`** — a perda seria invisível justamente para o endpoint que
existe para achá-la.

### Ciclo de vida — CONFORME (excedente)

| Item | Evidência |
|---|---|
| Transições no enum + máquina central | `StatusMissao` (13 transições), `MissaoStateMachine` — item E |
| `missao_evento` na mesma transação | `MissaoService.aplicar` salva missão e trilha no mesmo `@Transactional`; `ExpiracaoMissoesService` usa `saveAll` no mesmo lote |
| Autorização por operação | `EventoMissao`: PUBLICAR/CANCELAR/CONFIRMAR/CONTESTAR → CRIADOR · INICIAR/DESISTIR/CHECKIN → EXECUTOR · ACEITAR → CANDIDATO · RESOLVER_* → ADMIN · EXPIRAR → SISTEMA |
| Ator sempre do JWT | Verificado na F4: zero DTOs de entrada com id de usuário |
| Aceite concorrente | Lock pessimista `@Lock(PESSIMISTIC_WRITE)` (`MissaoRepository.java:54`), com a escolha justificada — inclusive **por que retry seria pior**: o estado já mudou para ACEITA, então repetir nunca sucede |
| Expiração agendada | `ExpiracaoMissoesJob` `@Scheduled`, com `SKIP_LOCKED` para não bloquear atrás de um aceite em curso |

| Teste exigido | Situação |
|---|---|
| Parametrizado com todas as transições, **inclusive inválidas** | **CONFORME (excedente)** — `MissaoStateMachineTest`, **118 testes**, matriz de 9 status × 11 eventos = 99 combinações. Cobre as inválidas afirmando `TransicaoInvalidaException` + status 409 **e** que a missão não sofreu mutação parcial |
| ABERTA → CONCLUÍDA nominalmente | **CONFORME** — `abertaNaoPodeSaltarParaConcluida`, teste próprio |
| Autorização, ator errado → 403, por operação | **CONFORME** — `atorErradoRecebeAcessoNegado` (parametrizado por evento) + `cancelarComoNaoCriadorDaAcessoNegado`, `iniciarComoNaoExecutorDaAcessoNegado`, `editarComoNaoCriadorDaAcessoNegado`, `resolverDisputaComoUsuarioComumDa403ENao500` |
| 50 threads no aceite, 1 vencedor | **CONFORME** — `MissaoAceiteConcorrenteTest`: `200: 1 \| 409: 49 \| 429: 0 \| 500: 0` |
| Mass assignment nomeando `status`, `executorId`, `xpRecompensa`, `tokensRecompensa` | **LACUNA (baixa)** — o teste envia `status`, `executorId`, `xpRecompensa` e `valorBrl`, e afirma que os quatro são ignorados. **`tokensRecompensa` não é nomeado** |
| Calculadora: determinismo, faixas, monotonicidade, teto | **LACUNA** — não há o que testar |
| `valorBrl > 0` em qualquer categoria → 400 | **CONFORME** — `nenhumaCategoriaAceitaValorEmBrl`, parametrizado nas 4 categorias |

**Sobre a qualidade do teste parametrizado** — vale registrar, porque é o melhor teste do
repositório: a tabela de transições esperadas é **escrita à mão, independente do enum**. O comentário
explica por quê: derivá-la de `StatusMissao` tornaria o teste tautológico, e ele continuaria verde se
alguém apagasse uma transição.

**Sobre a lacuna do mass assignment:** hoje ela é teórica, porque `tokensRecompensa` **não está** no
DTO de edição (`AtualizarMissaoRequest.java:17` lista explicitamente o que ficou de fora). Mas quando
o item A for corrigido e o campo sair também do DTO de criação, é exatamente essa assertion que
impedirá alguém de reintroduzi-lo — o mesmo papel que a assertion de `valorBrl: 499.99` cumpre hoje.

## Ordem por impacto

1. **Retirar `xpRecompensa` e `tokensRecompensa` de `CriarMissaoRequest`** (A) — fecha o vetor de
   abuso. Isoladamente, congela toda recompensa em zero, então só faz sentido junto com o item 2.
2. **`CalculadoraDeRecompensa` como função pura em `missoes/dominio`** (B), com parâmetros por
   properties. **Depende de `missao.complexidade`**, que a F3 aponta como ausente — as duas entram
   juntas.
3. **`versao_formula` gravada na criação** (C) — sem ela o valor é congelado mas não auditável, e
   mudar a tabela amanhã reinterpreta o passado. Coluna e calculadora têm de entrar no mesmo passo: a
   coluna sozinha é morta, a calculadora sozinha é irrastreável.
4. **`POST /missoes/previa-recompensa`** — depende inteiramente de 2. É também o que permite ao app
   mostrar o valor antes de criar, sem duplicar a fórmula no cliente (que reabriria a divergência por
   outro caminho).
5. **Nomear `tokensRecompensa` no teste de mass assignment** — trivial, e vira a rede de proteção
   dos itens 1–3.
6. **Tabela `pote` com `status RESERVADO/PAGO/DEVOLVIDO`** (F3, item 2) — torna a reserva explícita
   em vez de implícita no saldo, e é o que habilita o financiador PATROCINADOR da F8, sem o qual
   ENTREGA e AJUDA continuam cunhando.

Os itens 1 a 4 são **um único trabalho**, não quatro: retirar os campos sem a calculadora quebra a
criação de missão, e a calculadora sem a coluna de complexidade não tem insumo. Tratá-los em PRs
separados deixaria o sistema pior no intervalo.
