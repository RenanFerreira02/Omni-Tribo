## 5. Actuator na 8081, não na 8080 — CONFORME (excedente)

`application.yml:24-26` → `management.server.port: 8081`. Exposição limitada a `health,info,metrics`
(`application.yml:27-30`).

**Excedente sobre o pedido:** existe uma `SecurityFilterChain` dedicada à porta de gestão
(`SecurityConfig.java:71-88`, `actuatorFilterChain` com `@Order(1)`), liberando anonimamente apenas
`health` e `info` e mantendo `metrics` autenticado. Sem ela, o `anyRequest().authenticated()` da
cadeia principal alcançava a porta de gestão e `/actuator/health` respondia **401** — um health check

(3 testes) e conferido em execução: `health` → 200, `info` → 200, `metrics` → 401, e
`/actuator/health` na 8080 → 401 (não exposto).

## 6. Catálogo de `type` RFC 9457 — CONFORME (excedente)

**A especificação antecipa este item como a LACUNA de maior impacto. Ele está resolvido.**

`compartilhado/api/TipoProblema.java` é o catálogo, com 10 URIs estáveis:

| Constante | URI |
|---|---|
| `REQUISICAO_INVALIDA` | `https://omnitribo.dev/problemas/requisicao-invalida` |
| `NAO_AUTENTICADO` | `.../nao-autenticado` |
| `ACESSO_NEGADO` | `.../acesso-negado` |
| `NAO_ENCONTRADO` | `.../nao-encontrado` |
| `TRANSICAO_INVALIDA` | `.../transicao-invalida` |
| `REGRA_NEGOCIO_VIOLADA` | `.../regra-negocio-violada` |
| `CONFLITO_CONCORRENCIA` | `.../conflito-concorrencia` |
| `LIMITE_REQUISICOES` | `.../limite-requisicoes` |
| `NAO_IMPLEMENTADO` | `.../nao-implementado` |
| `ERRO_INTERNO` | `.../erro-interno` |

Os dois casos que a especificação nomeia como bloqueados estão cobertos e verificados em execução:

```
POST /carteira/saques  (flag desligada)
  → 422  "type": "https://omnitribo.dev/problemas/regra-negocio-violada"

POST /missoes  com valorBrl: 500
  → 400  "type": ".../requisicao-invalida"
         "errors": [{"campo":"valorBrl","mensagem":"Missão não remunera em BRL nesta versão…"}]
```

**O detalhe que mais importa para o app:** existem **três** caminhos que produzem erro, e os três
concordam. Além do `GlobalExceptionHandler`, há (a) os ~15 handlers herdados do
`ResponseEntityExceptionHandler`, cobertos por um override de `createResponseEntity`
(`GlobalExceptionHandler.java:49-69`) em vez de 15 sobrescritas — de modo que um handler novo do
Spring já nasce dentro do contrato; e (b) os escritores manuais de JSON em `SecurityConfig` e
`RateLimitFilter`, que rodam na cadeia de filtros, antes do DispatcherServlet, e produzem justamente
os 401 e 429 que o app mais recebe.

`ContratoErroTest` (7 testes) trava o contrato **por valor literal**, não pela constante — comparar
com `TipoProblema.X` faria o teste concordar com qualquer mudança nela, inclusive uma que quebrasse
todo app instalado.

**Granularidade a conhecer antes de integrar o app:** hoje é uma URI por *classe* de erro, não por
causa. Todo 422 é `regra-negocio-violada`, seja saque desabilitado, saldo insuficiente ou check-in
fora do raio. Para ramificar entre causas de um mesmo status, o caminho previsto é uma subclasse de
`DominioException` sobrescrevendo `getTipo()` com URI nova — **nunca** parsear `detail`. Está
documentado no javadoc de `TipoProblema`.

## 7. Nenhuma resposta vaza stack trace, SQL, classe ou driver — CONFORME

A especificação pede especificamente para procurar `ex.getMessage()` indo direto para `detail`.
Quatro ocorrências no handler, e **nenhuma vaza**:

| Linha | Contexto | Por que é seguro |
|---|---|---|
| 125 | `v.getMessage()` de `ConstraintViolation` | mensagem de Bean Validation, escrita por nós nos DTOs |
| 151 | `ex.getMessage()` de `BloqueioException` | exceção **nossa**, mensagem autorada |
| 164 | `ex.getMessage()` de `DominioException` | exceção **nossa**, mensagem autorada |
| 199 | `ex.getMessage()` em `log.info` | vai para o log, não para a resposta |

O handler genérico (`@ExceptionHandler(Exception.class)`) usa **string fixa** — "Erro interno.
Contate o suporte." — e envia a exceção só para `log.error`. É a fronteira certa: qualquer exceção
inesperada, inclusive de driver JDBC, cai ali.

Reforços: `application.yml:35-39` desliga `include-message`, `include-stacktrace`, `include-exception`
e `include-binding-errors` no error handler do servidor. E `ContratoErroTest` tem uma assertion
explícita de que o corpo de erro não contém `about:blank`, `com.omnitribo`, `Exception` nem
`org.hibernate`.

## 8. Correlation-id no MDC e no header — CONFORME

`compartilhado/infra/CorrelationIdFilter.java` aceita `X-Correlation-Id`, gera UUID quando ausente,
põe no MDC e devolve no header, com `MDC.remove` em `finally`. O padrão de log
(`application.yml:42-43`) inclui `[%X{correlationId}]`. Verificado em execução:

```
com header  → X-Correlation-Id: auditoria-f2-12345   (ecoado)
sem header  → X-Correlation-Id: 785df971-10a2-...    (gerado)
```

O mesmo valor sai como `traceId` em toda resposta de erro, o que liga a resposta ao log.

**Armadilha registrada, não defeito:** MockMvc não herda filtro auto-registrado por `@Component`, por
isso o `CorrelationIdFilter` é adicionado à mão em `MockMvcTestConfig`. Filtro novo exige decidir por
qual caminho ele entra — esquecer não quebra teste nenhum, só faz a suíte exercitar uma cadeia
diferente da que roda em produção.

## 9. ArchUnit existe e falha o build — CONFORME

`arquitetura/RegrasArquiteturaTest.java` aplica a regra aos 6 módulos de negócio:

```java
noClasses().that().resideOutsideOfPackage("com.omnitribo." + modulo + "..")
  .should().accessClassesThat()
  .resideInAnyPackage("com.omnitribo." + modulo + ".dominio..", "com.omnitribo." + modulo + ".infra..")
```

**Roda no `verify` e não está desabilitada** — `grep -c "@Disabled"` → 0:

```
[INFO] Running com.omnitribo.arquitetura.RegrasArquiteturaTest
[INFO] Tests run: 1, Failures: 0, Errors: 0, Skipped: 0 -- in ...RegrasArquiteturaTest
```

Violação faz `check()` lançar `AssertionError` → teste vermelho → build vermelho. A regra é **viva**,
não decorativa: ela é a razão de `MissaoService` injetar `RegistroCheckin` pela interface
(`geolocalizacao/api`) e não pela implementação — trocar por uma continuaria compilando e derrubaria
este teste.

**Duas propriedades a conhecer, ambas documentadas no CLAUDE.md:**
- `compartilhado` é **isento como alvo**, por ser shared por design. Violação dentro dele não é pega
  por teste nenhum — é disciplina.
- A regra é **direcional**: `compartilhado` continua sendo *origem*, e é por isso que
  `ConsultasGeoespaciais` não pode importar `Missao`/`StatusMissao`, recebendo status e categoria
  como String e devolvendo o par neutro `AlvoProximo`.

## 10. `TesteIntegracaoBase` com Testcontainers PostGIS — CONFORME (excedente)

`ContainerConfig.java` sobe `postgis/postgis:16-3.5` — a **mesma imagem do compose**, o que elimina
divergência entre teste e execução local. `grep -rn "h2\|H2"` no `pom.xml` e na configuração de
container: **nenhuma ocorrência**. Não existe H2 no projeto.

Excedente sobre o pedido, e cada item resolve um problema real:
- **Container singleton** em bloco `static`, em vez de `@Testcontainers`/`@Container` na classe
  abstrata — que iniciaria e pararia um container por classe concreta, e a segunda classe do mesmo
  contexto Spring encontraria o Hikari apontando para um container já parado.
- **Duas bases**: `TesteIntegracaoBase` (RANDOM_PORT) e `TesteIntegracaoMvcBase` (MOCK + MockMvc),
  para inspecionar headers sem roundtrip.
- **`max_connections=500`** no container, porque o consumo é (nº de contextos Spring × pool de 40), e
  cada `@MockitoBean`/`@MockitoSpyBean`/`@TestPropertySource` cria contexto próprio. O javadoc traz a
  aritmética — sem isso, a falha aparece como "Failed to load ApplicationContext", sem apontar a
  causa.

**Análise estática — é gate de verdade.** SpotBugs com `<effort>Max</effort>`,
`<threshold>Medium</threshold>` e `<failOnError>true</failOnError>`, ligado à fase `verify`. Achado
quebra o build como teste vermelho. Não é teoria: nesta rodada ele barrou duas vezes —
`NP_NULL_ON_SOME_PATH_FROM_RETURN_VALUE` e `DMI_RANDOM_USED_ONLY_ONCE` — e nos dois casos a correção
foi no código, não supressão do aviso. Spotless (Google Java Format) roda `check` no mesmo `verify`.

**CI** — `.github/workflows/api.yml` gera as chaves RSA (passo obrigatório: sem PEM nenhum contexto
Spring sobe, e sua ausência derrubaria toda a suíte de integração no GitHub enquanto tudo segue verde
local), roda `./mvnw verify` e arquiva o relatório JaCoCo. `.github/workflows/security.yml` roda
Gitleaks com `fetch-depth: 0` em todo push e PR.

**LACUNA:** o JaCoCo está configurado **só para relatório** — não há `<rule>`/`check` com mínimo de
cobertura, então uma queda não quebra o build. O `PULL_REQUEST_TEMPLATE.md` pede "cobertura não caiu"
como item manual de checklist. Impacto baixo hoje (88 %), e a especificação da F2 previa apertar os
gates na F12 — registro para que a decisão seja consciente e não esquecimento.
