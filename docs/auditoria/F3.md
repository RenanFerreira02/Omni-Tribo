# Auditoria F3 — Modelo de dados

**Data:** 2026-08-07 · **Branch:** `develop` · **HEAD:** `a3edef7`
**Método:** banco de pé, recriado do zero por `make reset` + boot da aplicação (15 migrations
aplicadas). Toda verificação foi feita executando **SQL real** contra o PostgreSQL 16.9 / PostGIS
3.5.2, incluindo `INSERT`/`UPDATE` de teste em transação com `ROLLBACK`. **Nenhum arquivo alterado.**

## Veredito

A especificação da F3 descreve um modelo **evoluído**, posterior ao ADR 0009 — e o schema atual
ainda é o anterior a essa evolução. O que existe está correto e verificado; o que falta é a
infraestrutura de **recompensa calculada e congelada** e a de **pote como agregado próprio**.

**Um DEFEITO** (imutabilidade do ledger é convenção, não garantia) e **quatro LACUNAS estruturais**
que, juntas, são a razão pela qual o defeito da F0 — cliente escolhe a própria recompensa — não tem
onde ser corrigido hoje.

| # | Item | Classificação |
|---|---|---|
| 6 | `UPDATE`/`DELETE` revogados no ledger | **DEFEITO** |
| 4 | `complexidade`, `versao_formula`, `multiplicador_risco` | **LACUNA** (alta) |
| 2 | Tabela `pote` | **LACUNA** (alta) |

## 2. Comparação coluna a coluna

### `missao` — 3 colunas faltando, 1 excedente

`\d+ missao` traz 28 colunas. Confronto com a especificação:

| Coluna da spec | Situação |
|---|---|
| id, criador_id, executor_id, categoria, titulo, descricao, status | ✅ tipos batem |
| peso_kg `numeric(6,2)`, volume_l `numeric(8,2)` | ✅ exatos |
| xp_recompensa `int`, tokens_recompensa `bigint` | ✅ existem — **mas não são calculados** (ver item 4) |
| valor_brl `numeric(12,2)` CHECK = 0 | ✅ com `ck_missao_economia` (V15) |
| origem/destino `geography(Point,4326)` | ✅ |
| ponto_custodia_id, cep, logradouro, bairro, cidade, uf | ✅ |
| raio_checkin_m `int default 50` | ✅ |
| janela_inicio, janela_fim, criada_em, aceita_em, concluida_em | ✅ todos `timestamptz` |
| versao `int` | ✅ |
| **complexidade** enum(LEVE,MEDIA,PESADA) | ❌ **LACUNA** |
| **versao_formula** `int` | ❌ **LACUNA** |
| **multiplicador_risco** `numeric(4,2)` | ❌ **LACUNA** |

**Excedente:** `pote_tokens bigint NOT NULL DEFAULT 0` — é o pote **como coluna**, o desenho que a
especificação substitui por tabela própria (abaixo).

### `pote` — tabela inexistente, **LACUNA alta**

```sql
SELECT to_regclass('public.pote');  →  (null)
```

Hoje o pote é a coluna `missao.pote_tokens`. A especificação pede um agregado com
`financiador_tipo enum(TRIBO,PATROCINADOR,NENHUM)`, `financiador_id`, `status
enum(RESERVADO,PAGO,DEVOLVIDO)` e `liquidado_em`.

**Por que isso importa e não é refinamento cosmético:** a coluna atual guarda um *saldo*, não um
*fato*. Ela não sabe **quem** financiou nem **em que estado** o dinheiro está. Duas consequências
diretas:

1. **`financiador_tipo = PATROCINADOR` é justamente o que falta** para fechar a pendência #3 do
   CLAUDE.md (ENTREGA/AJUDA cunham token). Sem a coluna, não há onde registrar que o pote de uma
   ENTREGA veio do patrocinador e não da tribo.
2. **`status RESERVADO/PAGO/DEVOLVIDO` tornaria o ciclo do pote auditável.** Hoje, quando uma missão
   é concluída, `pote_tokens` simplesmente decresce — não fica registro de que aquele valor foi
   *pago* em vez de *devolvido*. O estorno existe e funciona, mas a distinção só é reconstruível
   cruzando lançamentos.

### `lancamento` — motivos desatualizados, **LACUNA média**

Colunas: todas as da especificação presentes, com `chave_idempotencia` UNIQUE. Confronto do CHECK de
`motivo`:

| Motivo da spec | Situação |
|---|---|
| RECOMPENSA_MISSAO, TRANSFERENCIA_ENVIADA, TRANSFERENCIA_RECEBIDA, BONUS, ESTORNO, SAQUE | ✅ |
| **POTE_RESERVADO** | ❌ LACUNA |
| **POTE_DEVOLVIDO** | ❌ LACUNA |
| **RESGATE_BENEFICIO** | ❌ LACUNA |
| `FINANCIAMENTO_TRIBO` | ⚠️ **excedente**, é o antecessor de `POTE_RESERVADO` |

`RESGATE_BENEFICIO` é o motivo do **sumidouro** do token — o mecanismo que o ADR 0009 declara como a
peça que fecha a economia. Sem ele no CHECK, o resgate não tem como ser registrado no ledger.

### `carteira` — CONFORME

`id, usuario_id (UNIQUE), saldo_brl numeric(12,2), saldo_tokens bigint, versao int`. A especificação
lista `saldo_tokens` antes de `saldo_brl`; ordem de coluna é irrelevante. `saldo_brl` permanece,
conforme §4.6 da spec — e está em 0,00 em todas as seis carteiras (item 8).

### `identidade`, `geolocalizacao`, `logistica`, `compartilhado`

Todas conformes, com uma exceção:

- **`entrega_falida.peso_kg` e `volume_l` não existem** — **LACUNA baixa**. A especificação os pede
  para que a encomenda carregue as dimensões que alimentam o cálculo de complexidade. Hoje o peso e o
  volume só existem em `missao`, o que significa que **a conversão de entrega falida em missão
  precisaria adivinhar ou re-digitar esses valores** — exatamente o dado que deveria vir da
  transportadora.

## 3. `ck_missao_economia` cobre todas as categorias — CONFORME

```sql
ck_missao_economia | CHECK ((valor_brl = (0)::numeric))
```

A constraint não menciona categoria — vale para todas por construção. **Teste executado**, um
`INSERT` com `valor_brl = 10.00` por categoria, cada um em transação revertida:

```
CATEGORIA ENTREGA:  ERROR: new row violates check constraint "ck_missao_economia"
CATEGORIA COLETA:   ERROR: new row violates check constraint "ck_missao_economia"
CATEGORIA TRIBO:    ERROR: new row violates check constraint "ck_missao_economia"
CATEGORIA AJUDA:    ERROR: new row violates check constraint "ck_missao_economia"
CONTROLE (valor_brl = 0.00):  INSERT 0 1     ← passa, como esperado
```

Quatro rejeições e um controle positivo — a constraint está ativa e não é vacuamente verdadeira.

## 4. `complexidade` e `versao_formula` — LACUNA (alta)

```sql
-- ambas ausentes de \d+ missao
```

Também ausente `multiplicador_risco`.

**Esta é a lacuna estrutural mais importante do relatório**, e é a contraparte de banco do DEFEITO
apontado na auditoria F0 (`docs/auditoria/F0.md`, item 3a): o cliente envia `tokensRecompensa` e
`xpRecompensa`, o servidor grava sem recalcular, e ENTREGA/AJUDA cunham. Medido lá: 656 → 2656 tokens
em dois ciclos.

A especificação nomeia a solução em três colunas, e **cada uma resolve um problema distinto**:

- **`complexidade`** é a *entrada* da fórmula. Sem ela, não há de onde derivar a recompensa: peso e
  volume sozinhos não distinguem "mutirão de pintura" de "carregar armário".
- **`versao_formula`** é o que permite **congelar** a recompensa. Se a tabela de recompensa mudar
  depois, missões antigas não podem ser reinterpretadas — e sem registrar qual fórmula produziu
  aquele valor, é impossível auditar retroativamente se um crédito estava certo. É o mesmo princípio
  do `saldo_apos_*` no ledger: guardar o resultado *e* o contexto que o produziu.
- **`multiplicador_risco`** (F11) precisa ser congelado junto pelo mesmo motivo.

**Ordem de dependência que vale notar:** `versao_formula` sem `CalculadoraDeRecompensa` é coluna
morta, e a calculadora sem a coluna produz valores irrastreáveis. As duas têm de entrar juntas.

## 5. `chave_idempotencia` UNIQUE — CONFORME

```
 uk_lancamento_idempotencia

INSERT 0 1                                    ← primeiro
ERROR: duplicate key value violates unique constraint "uk_lancamento_idempotencia"   ← segundo
```

A garantia é **do banco**, não da aplicação. `MigracaoTest` cobre o mesmo caminho afirmando
`DuplicateKeyException` e o nome da constraint — de propósito, e não a superclasse
`DataIntegrityViolationException`, que deixaria o teste verde se a UNIQUE fosse derrubada e o INSERT
falhasse por qualquer outro motivo.

## 6. `UPDATE`/`DELETE` no ledger — **DEFEITO**

A especificação antecipa corretamente: *"Se não estiverem, é DEFEITO: a imutabilidade do ledger vira
convenção em vez de garantia."* É exatamente o caso.

**Como `omnitribo_app` (o papel restrito que as migrations criam):**
```
UPDATE lancamento SET valor_tokens=999;  → ERROR: permission denied for table lancamento
DELETE FROM auditoria;                   → ERROR: permission denied for table auditoria
```

**Como `omnitribo` (o usuário que a aplicação de fato usa):**
```
BEGIN; UPDATE lancamento SET valor_tokens=999;
UPDATE 8
 linhas_alteradas
------------------
                8
```

**O `REVOKE` está correto e é inerte.** `application.yml`, `application-dev.yml` e
`application-test.yml` conectam como `omnitribo`, dono das tabelas, para quem GRANT e REVOKE não se
aplicam. O comentário em `V5__carteira.sql` descreve a proteção como *"defesa em profundidade"* — e
essa defesa não está ligada.

Hoje a imutabilidade do ledger é sustentada só pela disciplina do `LivroRazaoService`. Isso é uma
convenção forte e testada, mas é convenção: um `save()` numa entidade `Lancamento` já persistida
passaria sem obstáculo do banco.

Já rastreado como pendência #2 do CLAUDE.md, com a decisão consciente de fechar na F12. O fechamento
exige `spring.flyway.user` separado, porque `omnitribo_app` não tem DDL nem acesso a
`flyway_schema_history`. `MigracaoTest` já trava a matriz de privilégios, então a metade que existe
não regride em silêncio.

## 7. Índices GiST e `EXPLAIN ANALYZE` — CONFORME

```
          indice          |     tabela
--------------------------+----------------
 idx_checkin_ponto        | checkin
 idx_missao_origem        | missao
 idx_ponto_custodia_ponto | ponto_custodia
```

Os dois exigidos (`missao.origem`, `ponto_custodia.ponto`) mais `checkin.ponto`, excedente.

**Plano real, com `enable_seqscan = on`** — o índice foi escolhido pelo planner, não forçado:

```
 Sort (actual time=4.744..4.745 rows=10 loops=1)
   ->  Index Scan using idx_missao_origem on missao m (actual time=4.718..4.735 rows=10 loops=1)
         Index Cond: (origem && _st_expand(...,'2000'::double precision))
         Filter: st_dwithin(origem, ..., '2000', true)
         Rows Removed by Filter: 1
 Execution Time: 4.775 ms
```

`Index Scan`, sem `Seq Scan` em nenhum nó. O padrão `Index Cond` (bounding box `&&`) + `Filter`
(`ST_DWithin` exato) é o comportamento correto do PostGIS: o índice reduz o candidato pela caixa e o
filtro faz o refino métrico — visível nos `Rows Removed by Filter: 1`.

O plano acima roda sobre as 12 missões do seed. A evidência sobre volume está em
`docs/evidencias/f6-explain-analyze.md`: **200 mil linhas em 21 ms**, com `ANALYZE` e sem tocar em
`enable_seqscan`.

### 8c. Recompensa sem lançamento correspondente — **DEFEITO de dado**

A pergunta da especificação encontrou uma inconsistência real. Uma missão tem **dois** lançamentos de
`RECOMPENSA_MISSAO`:

```
missão: "Mutirão: pintura da escada de serviço do Ed. Pinheiros Verde"
        categoria TRIBO · tokens_recompensa = 50 · executor = erik · status CONCLUIDA

 handle |  sinal  |      motivo       | valor_tokens |    chave_idempotencia
--------+---------+-------------------+--------------+---------------------------
 diana  | CREDITO | RECOMPENSA_MISSAO |          100 | seed-idem-diana-t1-tokens
 erik   | CREDITO | RECOMPENSA_MISSAO |           50 | seed-idem-erik-t1-tokens
```

**Diana não é a executora dessa missão, e recebeu 100 tokens de recompensa por ela** — o dobro do que
a missão paga. O lançamento está em `V900__seed_dev.sql:460-464`, apontando
`missao_id = dddddddd-...-008`.

Duas leituras possíveis, e nas duas é defeito:
- Se a intenção era creditar diana por outra missão TRIBO, o `missao_id` está errado (a
  `dddddddd-...-009`, "Mutirão: instalar trilho de LED", tem 80 tokens e **nenhum executor**).
- Se a intenção era esta missão, o valor contradiz `tokens_recompensa`.

**Por que a reconciliação não pega:** ela soma ledger e compara com `saldo_tokens`, e isso bate
perfeitamente — diana tem 170, e o ledger dela soma 170. O que está incoerente é a relação
*missão ↔ recompensa ↔ executor*, que nenhuma invariante hoje verifica. É a mesma classe de ponto
cego descrita no ADR 0009: consistência não é conservação, e nenhuma das duas é coerência de
domínio.

Impacto real hoje: baixo, é dado de demonstração. Mas a missão em questão é a que o app usaria para
ilustrar o mutirão comunitário, e um extrato mostrando "recompensa de missão" para quem não executou
é exatamente o tipo de detalhe que uma banca nota.

### 8d. Observação sobre potes no seed

As três missões TRIBO estão com `pote_tokens = 0`, inclusive a CONCLUIDA que pagou 50 tokens. Como o
seed insere estado final, não há registro de que aquele pote tenha sido financiado — os 50 tokens de
erik aparecem no ledger como crédito sem débito correspondente em carteira nenhuma. **Não é violação
da conservação medida** (o total do seed é o estado inicial por definição), mas significa que o seed
**não demonstra o ciclo de financiamento**, que é a mecânica central da economia do cuidado. Registro
como observação, não como achado — a spec não exige potes semeados.

## 9. Excedentes — 6 colunas, todas justificadas

| Coluna | O que faz |
|---|---|
| `missao.pote_tokens` | O pote **como coluna** — o desenho que a spec substitui pela tabela `pote`. Não é excedente gratuito: é o antecessor direto do item que falta. |
| `lancamento.mensagem` | Texto opcional que o remetente anexa a uma transferência P2P. Exposto no extrato; a chave de idempotência não é exposta. |
| `checkin.chave_idempotencia` | UNIQUE, guarda `sha256(usuario\|missao\|chave_do_cliente)` — nunca a chave crua, porque a UNIQUE é global e um cliente mandando `"1"` receberia o replay do check-in alheio. Adicionada na V12. |
| `checkin.suspeito` | Marca check-in aceito porém com cinemática implausível (> 120 km/h). Separado de `valido` de propósito: suspeito **não** rejeita, sinaliza para revisão. |
| `outbox.proxima_tentativa_em` | Backoff exponencial do drenador (30 s, 1, 2, 4, 8 min). Sem ela, evento com falha permanente seria reprocessado em cada varredura de 10 s. |
| `outbox.ultimo_erro` | Guarda a causa da última falha de despacho, para diagnóstico sem precisar correlacionar log por timestamp. |

Nenhuma tabela excedente. `flyway_schema_history` e `spatial_ref_sys` são de infraestrutura.

## Ordem de correção recomendada

1. **`complexidade` + `versao_formula` + `CalculadoraDeRecompensa`** (item 4) — bloqueia a correção
   do DEFEITO da F0. Precisam entrar juntos: a coluna sem a calculadora é morta, a calculadora sem a
   coluna é irrastreável. Enquanto não existirem, o teto de emissão de TOKEN é o arbítrio do cliente.
2. **Tabela `pote` com `financiador_tipo` e `status`** (item 2) — desbloqueia o patrocinador da F8,
   que é o que fecha a conservação para ENTREGA/AJUDA. Migração a partir de `missao.pote_tokens`.
3. **Motivos `POTE_RESERVADO`, `POTE_DEVOLVIDO`, `RESGATE_BENEFICIO`** (item 2) — o terceiro é o
   sumidouro do token; sem ele o resgate não tem como ser lançado. Migração de CHECK, com
   `FINANCIAMENTO_TRIBO` convivendo até os dados serem convertidos.
4. **Corrigir o lançamento de diana no seed** (item 8c) — dado, não schema; correção rápida e visível
   no extrato do app.
5. **`entrega_falida.peso_kg` / `volume_l`** (item 2) — necessário antes de a conversão
   entrega→missão alimentar a calculadora de complexidade.
6. **Datasource como `omnitribo_app` + Flyway com usuário próprio** (item 6) — já decidido para a
   F12. É o que transforma a imutabilidade do ledger de convenção em garantia.
